You are the next implementation agent on the Runway 90 iPhone app. Build a
careful, trauma-informed first-run onboarding flow after authentication. Do not
rewrite the existing sponsor loop or the entry/auth screen unless a small
integration change is required.

## Objective

After a user signs in or creates an account, show a detailed but calm
onboarding sequence for a new account. Returning users who have already
completed onboarding must go directly to their normal role route. The flow
must work in both local demo mode and live Auth0 mode.

The onboarding should explain what Runway 90 is, establish user control, set
safe defaults, and finish with one clear next step: review the synthetic demo
letter. It must not ask a survivor to recount abuse or enter real financial
account information.

## Required flow

Implement these pages in this order, with Back and Continue controls:

### 1. Welcome

Title: `Welcome to Runway 90`

Explain in plain language:

> Runway 90 helps you organize the first steps of financial recovery after
> leaving an unsafe or controlling situation.

Include a small progress indicator such as `1 of 5`. Keep the copy short and
reassuring. Do not use urgent language, legal promises, or financial advice.

### 2. Privacy and safety

Explain that:

- The demo uses fictional data only.
- Documents are not treated as facts until the user confirms them.
- The app has a quick exit via Exit/shake/triple-tap.
- The decoy screen can hide the app quickly if the phone is being watched.

Add a clear acknowledgement control:

`I understand how quick exit works`

The Continue button must remain disabled until this is checked. Do not imply
that quick exit guarantees physical safety.

### 3. How the recovery loop works

Show the five steps as a compact vertical timeline or cards:

1. Capture a document.
2. Review the extracted details.
3. Decide Mine, Not mine, or Not sure.
4. See one next action and the runway estimate.
5. Share only the neutral summary the user approves.

State explicitly that the user is the source of truth and the app never labels
an account `fraud`.

### 4. Personalization without sensitive collection

Ask only for low-risk preferences:

- Preferred display name.
- Whether the user wants the demo letter ready on the home screen.
- Whether the user wants the app to remember the local demo session on this
  device.

Do not ask for a real address, employer, bank, creditor, abuser name, case
number, income, account number, or detailed story. Use the existing fictional
Maya defaults when the user leaves values unchanged.

For live Auth0 accounts, prefer the Auth0 profile name and keep any local
preference keyed by the verified Auth0 `sub`. For demo accounts, key it by the
demo subject generated by `AuthAdapter`.

### 5. Ready screen

Title: `You are in control`

Summarize the choices the user made and show exactly one primary action:

`Review the demo letter`

That action should route to the existing capture/review flow. Include a small
secondary text action to skip for now and go to Home. The screen must retain
the compact copy `Contents produced are for demo only.`

## State and routing requirements

Add an explicit onboarding state rather than inferring completion from the
case fixture. At minimum, track:

- `hasCompletedOnboarding`
- `completedAt`
- `displayName` if the user changed it
- `showDemoLetterOnHome`
- `rememberDemoSession` for demo mode only

Persist completion per authenticated subject. A UserDefaults key such as
`runway90.onboarding.completed.<subject>` is acceptable for the hackathon;
do not use one global boolean that could leak one user's onboarding state to a
different user. If the state belongs in `CaseState`, preserve Codable backward
compatibility for existing saved fixtures.

Routing rules:

- New survivor account → onboarding → survivor Home or Capture when the user
  taps the primary action.
- Returning survivor with completed onboarding → survivor Home directly.
- Advocate sessions → do not show survivor onboarding; keep the scoped
  advocate route.
- Logout → clear the active session, but do not erase completed onboarding
  unless the user explicitly uses Delete demo case.
- Delete demo case → clear demo onboarding and return to disclosure.
- If onboarding is interrupted, reopen it at the last incomplete page without
  exposing case data.

## Visual and interaction rules

- Keep the existing Runway 90 palette and `.rwScreen()` background.
- Use `.glassCard()` for cards and `.rwPrimaryButton()` / `.rwGlassButton()`
  for buttons. Do not introduce raw button styles in views.
- Keep deployment target at iOS 18.0. Gate iOS 26 Liquid Glass APIs with
  `#available(iOS 26.0, *)`.
- Preserve the attached pink/blue grid image for the entry screen; do not use
  it as a distracting full-bleed onboarding background unless it remains
  readable and accessible.
- Preserve the centered plain-text `Exit` control on the entry screen.
- Keep the synthetic disclaimer visible on onboarding.
- Support Dynamic Type, VoiceOver labels, Reduce Motion, and safe-area insets.
- Do not put private case details, document previews, or financial amounts in
  onboarding previews.

## Hard safety and product constraints

- Synthetic data only. Never put real names, accounts, or documents in tests.
- Never use the word `fraud` in user-facing copy.
- Never add a real financial or legal claim.
- Never send API keys to the iPhone or commit secrets.
- Never expose an advocate to survivor onboarding state or private notes.
- Do not silently switch a live Auth0 session into a demo session.
- Keep all fallback labels honest: `Demo Auth0`, `Demo extraction`, `Demo
  memory fallback`, or `Demo data source` as appropriate.
- Keep exactly one primary next action on the eventual Runway screen.

## Acceptance checklist

Verify all of the following:

- Fresh demo account sees all five onboarding pages.
- Continue is disabled on the safety acknowledgement page until checked.
- Back navigation preserves entered preferences.
- Relaunching after completion skips onboarding for the same subject.
- A different demo account does not inherit the previous account's completion.
- Logout returns to the entry screen and does not erase onboarding completion.
- Delete demo case clears onboarding and returns to disclosure.
- Live Auth0 login uses the verified subject and does not use Maya's local
  subject or fixture as the owner key.
- Advocate login never enters survivor onboarding.
- Quick exit works from every onboarding page.
- `Contents produced are for demo only.` remains visible.
- The five-beat demo still works after onboarding is complete.
- `git diff --check` passes.
- The simulator build succeeds with:

```sh
xcodebuild -project Runway90.xcodeproj -scheme Runway90 \
  -destination 'generic/platform=iOS Simulator' build CODE_SIGNING_ALLOWED=NO
```
